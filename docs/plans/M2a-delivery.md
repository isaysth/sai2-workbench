## 1. 现在能做什么

1. **设置 → 监听目录**：多选添加文件夹、逐条移除、含子目录开关、勾选监听哪些扩展名、立即重扫。
2. 往目录里丢 `sai2 / psd / png / jpg / webp`，**0.9 秒内**卡片自己冒出来；删掉文件 **0.5 秒内**消失；在画图软件里覆盖保存，缩略图跟着更新。
3. 卡片上全是**真缩略图**：SAI2 解文件自带的预览块，PSD 取合成图，图片原生解码 —— 不装任何外部工具。
4. 瀑布流按修改时间倒序排列，窗口拉宽列数自动变多；1000 条滚动零卡顿。
5. 出不了图的文件显示**信息卡**（后缀 + 画布尺寸 + 大小 + 修改时间）；有同名图片的自动当封面并标「封面」。
6. 缩略图落盘缓存，重启不重解；设置页能看到占用、一键清空；超 2GB 自动淘汰最旧的。

## 3. 关键实现决定

### 3.1 缩略图请求只用一个 URL

渲染端统一写 `<img src="sai2img://thumb/<key>.jpg">`，**后缀是假的** —— 缓存文件可能是 jpg 也可能是 png，
协议层按 key 反查真实文件。好处是渲染端不用先问主进程"这张是什么格式"，少一轮 IPC，首屏快一截。

### 3.2 缓存键 = sha1(版本|大小|修改时间|路径)

- 带 `mtime` + `size`：覆盖保存会自动失效，不会出现"存了盘但预览还是旧的"。
- 带 `thumbVersion`：改解码逻辑后 +1，全量失效，用户不用手动清缓存。
- **不带目标像素**：初版把卡片尺寸也放进哈希，结果拖动大小滑块就整个缓存作废、一千张重解。改成固定长边 512、一份缓存通吃所有尺寸。

### 3.3 图片直通，别硬解

PNG/JPEG 用 `nativeImage` 缩放；WebP/BMP/GIF 主进程解不了，直接把原文件流给浏览器。
Chromium 的解码器比任何 JS 库都快，而且这条正好绕开 v1.19 那个"WebP 解码失败"的坑。

### 3.4 扫描期间的事件要缓冲

全量扫描是快照遍历，扫到一半新建的文件可能落在**已经遍历过**的目录里。直接应用会被后续批次覆盖掉
（表现为"新文件偶尔不出现在列表里"）。做法：扫描期间只记路径，扫完统一回放并比对 mtime。

### 3.5 变更合并 120ms，按 path 增量应用

一次复制 500 个文件，watcher 会吐几百个事件。合并成一批推送，渲染端按 path 合并进 Map
（不是整体替换，否则滚动位置会丢）。

## 4. 与计划的偏差

| 计划 | 实际 | 原因 |
|---|---|---|
| 缓存键含 `targetPx` | 去掉，固定长边 512 | 拖卡片大小滑块会全量重解 |
| `thumb://` 协议 | 复用 `sai2img://` 加 `thumb` host | 不新增 scheme，权限配置只维护一套 |
| 信息卡高度 3:4 | 按 `canvas` 比例 | 256×256 的小画布占 3:4 大白块很丑 |
| PSD 全部走 worker | 仅 >20MB 走 worker | 小 PSD 主进程解只要几毫秒，起线程反而更贵 |
| 瀑布流"先 CSS columns 保底" | 直接上虚拟滚动 | 自算坐标一次到位，实测 0 长任务，没走保底 |

## 5. 留给下一步的已知限制

1. **小画布 SAI2（`intg`/`dpcm`）不出图**，走信息卡。要做需展开 256×256 分块 + 行差分 + 变长 RLE16，估 1.5 天。
2. **`.clip` / `.kra` 不出图**，走信息卡 —— 等 M3a 的 `thumb-shell` 插件。
3. **列表一次最多 2 万条**（`files:list` 上限）。5 万文件的目录只显示最新的 2 万，分页留给 M2b。
4. **网络盘 / OneDrive** 收不到事件的风险仍在，未做 30 秒轮询降级（计划 §5 风险 4）。
5. **搜索框仍是禁用状态**，关键词过滤在 M2b 做。

## 6. 怎么自己验

1. `env -u ELECTRON_RUN_AS_NODE npm start`（**必须带 `env -u`**，否则 Electron 被当成纯 node 跑）。
2. 设置 → 监听目录 → 添加文件夹，选一个装稿子的目录。
3. 回到文件页：卡片应该在两秒内出现。
4. 丢一个新文件进去 → 卡片自己冒出来；删掉 → 自己消失。
5. 设置 → 缩略图 → 清空缓存 → 回文件页，图会重新生成一遍。
