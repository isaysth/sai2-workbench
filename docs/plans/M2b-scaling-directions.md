# 稿件规模增长 · 体验优化方向（待确认）

> 触发：用户提出「目前稿件少可以精准定位，后续稿件增多该怎样优化体验」
> 状态：**仅方案，代码零改动**（按开发文档 §1.2，确认后再排期、再动代码）
> 关联需求：F2 监听文件夹 / F5 标签 / F9 搜索 / F16 设置页
> 本轮已落实的三项（不在本方案内）：默认仅启动时扫描、文件页「刷新」按钮、筛选工具条
>
> **已确认的输入（v2）**
> - 预计量级：**5 千份**
> - 找图方式：**时间段 / 项目或客户 / 标签**（三者都用，**不靠记文件名**）
> - 本地数据库：**可以接受**（`data/index.db`）
> - 结论：**文件名检索降级，组织（项目·客户·标签）+ 时间视角升为主要方向**；SQLite 一次做到位，不做「先 JSON 后迁移」

## 1. 先看清瓶颈在哪

M2a 实测基线：1006 文件 / 7 目录首扫 **156ms**；1000 条滚动 **0 个长任务**、常驻 **33 个 DOM 卡片**；缩略图缓存 904 张约 3.25MB（压测上限 4MB 时）。
这个基线在千级是宽裕的，但当前架构有六条硬约束，规模一上去会依次暴露：

| # | 现状 | 为什么会成为瓶颈 |
|---|---|---|
| 1 | `files:list` 一次把**全量** `ProjectFile` 序列化给渲染端（上限 2 万条） | 启动时间、内存、IPC 载荷都随条数线性涨；超过 2 万条尾部文件根本拿不到 |
| 2 | 过滤/排序在**渲染端**对全量数组做 O(n) | 每敲一个字都 filter + 重排瀑布流，万级开始有输入延迟 |
| 3 | 瀑布流坐标每次筛选/量到新比例都全量重算 O(n) | 条数越多，一次筛选的卡顿越明显 |
| 4 | 索引**不落盘**，每次启动全量 readdir + stat | 5 万条要几十秒，没有「秒开」的可能 |
| 5 | 主键是 `path` | 改名 / 移动 = 删旧加新；将来加标签必然「一改名标签就丢」（需求 F5 明确禁止） |
| 6 | 只有「最近修改」一个秩序 | 没有标签、项目、状态、评分、智能集合；稿子一多只能靠肉眼翻 |

**拐点预估**（按当前实现的推算，不是实测）：

| 稿件量 | 最先坏的东西 | 用户体感 |
|---|---|---|
| ~1 千（现在） | 无 | 顺畅，滚动零掉帧 |
| ~5 千 | 全量下发 JSON、输入重排、缩略图缓存体积 | 启动 1~2s，敲关键词偶有顿感 |

> 注：上表是「维持现状、不加数据库」的外推。你的实际量级是 5 千，按 P1 落盘后启动走读库路径，目标 ≤1s；5 千也不会触及 `files:list` 的 2 万上限。
| ~2 万 | 渲染端内存、`files:list` 2 万上限、O(n log n) 排序 | 启动明显慢，尾部文件看不到 |
| ~10 万+ | 索引不落盘、缓存淘汰、坐标数组 | 基本不可用 |

**升级触发线**（任一持续出现就该进 P1）：启动到出卡片 > 2s；输入到列表更新 > 100ms；渲染端常驻 > 300MB；缩略图缓存 > 1GB。

## 2. 五个优化方向

### 方向 A · 检索层：从「翻」变成「搜」（建议最先做）

| 项 | 内容 | 解决什么 |
|---|---|---|
| A1 | 过滤/排序**下推主进程**：文件名 n-gram 倒排、拼音首字母、模糊匹配（错别字/简繁） | 敲字不再 O(n) 扫全量；中文短词、拼音也能命中 |
| A2 | **索引落盘**：SQLite 存 path/size/mtime/ext/canvas/thumbKey/元数据，启动读库秒开，只做增量校验（mtime+size 比对），全量扫描退化为兜底 | 5 万条也能秒开；为标签提供落脚点 |
| A3 | 搜索语法 `name:` `ext:` `dir:` `before:` `after:`、`Ctrl+F` 聚焦、结果高亮、最近搜索 | 组合条件精准定位，不必点一串下拉 |
| A4 | **分页 / 窗口查询**：主进程按「筛选 + 排序 + offset/limit」返回一段，渲染端只持有可视窗口和总数 | 内存与 IPC 不再随总量增长，10 万条也能滚 |

代价：引入本地 DB（原生依赖 + 几十 MB 的 `data/index.db`），要设计版本迁移与损坏自愈（配置模块已有原子写 + 坏文件重建的现成套路可复用）。
备选：不想上原生依赖时先用轻量 JSON 索引 + 倒排文件，但 5 万条以上仍会退化，**只适合 5 千级**。

### 方向 B · 组织层：给文件加「人」的信息

- 标签 / 评分 / 颜色标记 / 状态（草稿·进行中·完成）/ 备注 / 自定义字段。
- **文件身份**：主键从 `path` 换成「卷序列号 + 文件 ID」或内容指纹，改名移动后标签不丢（F5 的硬要求）。
- **智能文件夹**：把当前筛选组合存成一个入口（例：「今年的 SAI2 线稿」），一键回到该视角。
- 手动封面、合集、按项目/客户分组。
- **依赖 A2**：没有持久化索引，标签只能塞在配置文件里，改名必丢、量大了也慢。

### 方向 C · 交互层：少滚动、能定位

- 目录树 / 面包屑、按年月分组折叠、时间轴刻度条（拖到某个月）。
- 键盘导航（方向键选卡、Enter 打开、F2 改名、Ctrl+F）、多选批量、右键菜单、拖到文件夹归类。
- 最近打开、收藏置顶、「跳到上次位置」。
- 纯导航部分不依赖 DB，可与 A 并行先做；收藏/项目依赖 B。

### 方向 D · 渲染与缓存：让 10 万条也不掉帧

- 缩略图**分级**：128px 列表小图 + 512px 详情大图，先出小图再渐进换；按当前卡片尺寸选级，缓存体积可降一个数量级。
- 只为「当前筛选结果的可视区」生成缩略图，取消已滚出 / 被筛掉的请求；缓存键脱离路径（用内容指纹），改名不重解。
- 过滤/排序放 worker、主线程只收结果；瀑布流坐标按列增量维护，不每次全算。
- 缓存分层：热数据内存 LRU + 冷数据磁盘，按「最后访问」而非仅 mtime 淘汰。
- 改动集中在 `thumbs/` 与 `useMasonry.ts`，可独立排期，风险中等。

### 方向 E · 数据规模：归档与去重（优先级最低）

- 归档库（冷数据移到别处仍可搜）、重复文件检测（内容指纹）、按目录设「只索引不生成缩略图」、排除临时文件。
- 需求已明确不做联网，此项只考虑本地多盘 / 移动硬盘场景。

## 3. 落地顺序（按 5 千 + 时间/项目客户/标签 收敛）

**先明确 5 千不需要什么**（避免过度设计，这三项直接不做）：

| 原方向 | 5 千是否需要 | 原因 |
|---|---|---|
| A4 分页 / 窗口查询 | **不需要** | 5 千条 `ProjectFile` 约 1.5MB，一次下发仍是毫秒级；分页会显著增加滚动与筛选的复杂度 |
| A1 文件名 n-gram 倒排 | **不需要** | 主进程线性 filter 5 千条 < 1ms；你也不靠文件名找图 |
| D 过滤放 worker | **不需要** | 量级没到，worker 通信反而可能比计算本身更贵 |

**要做的（按顺序）**：

| 阶段 | 做什么 | 关键理由 | 主要改动 |
|---|---|---|---|
| P0 ✅ 已做 | 筛选工具条 + 手动刷新 + 扫描方式可选 | — | `FilesPage` / `store/files` / `FilesIndex` |
| **P1（建议下一步）** | **数据底座 + 组织**：SQLite 索引落盘（含文件身份）、标签池、项目/客户归属、详情面板可编辑、筛选条接入「标签 / 项目 / 时间」 | 你三个维度里两个（项目客户、标签）目前根本不存在；标签又必须挂在不随路径变的身份上，所以底座和标签必须同批做 | 新增 `src/main/db/`、`files:list` 补 `tags/project` 字段、详情面板加编辑区、`Filters` 加两个维度 |
| P2 · 视角与直达 | 按年月分组 + 时间轴刻度、**智能文件夹**（把「客户 A + 今年 + 未完成」存成一个入口）、Ctrl+F、最近打开/收藏置顶 | 时间是你的第一个维度，`mtime` 已有，不需要额外数据；智能文件夹等于把「项目+时间+标签」的组合常态化 | `useMasonry` 加分组、侧栏加入口列表、db 加 `smart_folders` 表 |
| P3 · 规模与观感 | 缩略图分级（128 列表级 / 512 详情级）、缓存按「最后访问」淘汰、坐标增量维护 | 5 千 × 约 30KB ≈ **150MB** 缓存，体积和首屏都要压一压；但这是体感问题，不是可用性问题 | `thumbs/` 缓存键与分级、`useMasonry.ts` |
| P4 · 归档去重 | 冷数据归档、内容指纹去重、多盘 | 按需 | 新增归档模块 |

### P1 的技术选择（已定）

- **数据库**：`node:sqlite`（Node 24 内置，无原生编译、无 `better-sqlite3` 打包风险）或 `better-sqlite3`。优先内置，装不下再退。
- **表结构**（草案）：
  - `files(id, path, dir, name, ext, size, mtime, file_id, volume, width, height, thumb_key, first_seen)`
  - `tags(id, name, color)` + `file_tags(file_id, tag_id)`
  - `projects(id, name, client, color)` + `files.project_id`
  - `meta(file_id, rating, status, note)`
  - `smart_folders(id, name, query_json)`
- **文件身份**（改名/移动不丢标签，F5 硬要求）：`volume + file_id`（Windows `fs.stat` 的 `dev` + `ino`）为主键之一；改名后 `ino` 不变 → 标签跟着走。**兜底**：内容指纹（头尾各 64KB + size 的 sha1），应对跨盘复制。
- **启动策略**：先读库出卡片（目标 < 300ms），再后台做一次 mtime+size 校验，差异项才重新解析；全量扫描退化为兜底入口。
- **迁移**：`data/index.db` 带 `schema_version`；版本不符则重建索引（不丢标签，标签在独立表且按 file_id 关联，重建时按 `path+ino` 回填）。

### P1 验收口径

| 项 | 标准 |
|---|---|
| 5 千条启动到出卡片 | ≤ 1s（读库路径） |
| 打标签到列表出现标签筛选结果 | ≤ 200ms |
| 改名文件后标签仍在 | 100%（手工改名 + 在同目录移动各测 3 次） |
| 改用筛选「项目 + 时间 + 标签」组合 | 命中数与肉眼核对一致 |
| 索引文件损坏 | 自动重建，不弹错误、不丢标签 |

## 4. 决策已定稿（2026-11-17）

| 议题 | 结论 |
|---|---|
| 稿件量级 | **5 千** |
| 找图方式 | **时间段 / 项目或客户 / 标签**（三者并用，不靠文件名） |
| 本地数据库 | **接受** `data/index.db` |
| 项目 / 客户建模 | **选项 A**：一个「项目」= 名字 + 可选客户字段，文件只归属一个项目 |
| 标签来源 | **选项 A**：手动标签 + 目录自动映射（可改可删） |

补充口径（由上面两条直接决定）：

- **项目表**：`projects(id, name, client, color, archived)`；`files.project_id` 单值外键。客户不是独立维度，只是项目上的一个可筛字段，所以筛选条仍是「项目」一个下拉 + 一个「客户」下拉（客户由项目表 distinct 出来）。
- **自动映射**：目录 → 标签规则存 `auto_tag_rules(dir_prefix, tag_id)`。规则只在**首次入库**和**目录变更**时套用，之后文件被手动改过的标签以手动为准（`file_tags.source = 'auto' | 'manual'`，手动覆盖时不删 auto 记录，只是隐藏）。
- **不做的**：多选项目、标签层级（父子标签）、标签自动学习（按文件名猜）。5 千量级用不上，做了反而增加心智负担。
